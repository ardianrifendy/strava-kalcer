# PRODUCT

Application name:

**Strava Kalcer**

This is NOT a simple GPX-to-FIT converter.

It is a **GPX-based activity reconstruction and simulation engine** that creates a complete, internally consistent activity from an existing route.

Core pipeline:

**IMPORT GPX**
→ **ROUTE REVIEW**
→ **ROUTE INTELLIGENCE**
→ **ACTIVITY SETTINGS**
→ **SIMULATION**
→ **SIMULATION PREVIEW**
→ **DEVICE PROFILE**
→ **FIT GENERATION**
→ **FIT VALIDATION**
→ **SAVE / SHARE**

The user should feel that they are creating a complete activity from a route, not editing a spreadsheet of values.

---

# USER-VISIBLE PRODUCT VALUE

The application must prominently communicate these capabilities:

### Recreate Your Ride
Turn a GPX route into a complete simulated activity.

### Target Your Average
Set a target average speed or running pace. The engine distributes performance realistically across the route rather than forcing constant speed.

### Realistic Uphill & Downhill
Performance responds naturally to gradient and terrain.

### Find Your Fastest Downhill
Analyze the real route and identify sections that can naturally produce high speed.

### Ride or Run Your Style
Use activity profiles such as Easy, Endurance, Tempo, Race, Fondo, Climb, Long Run, Intervals and Custom.

### Heart Rate Simulation
Generate a continuous HR profile responding to effort, terrain and recovery.

### Natural Cadence
Generate cadence that corresponds to speed, terrain and effort.

### Synchronized Activity Graphs
Map, elevation, speed/pace, HR and cadence must all follow the same route position/time.

### Multiple Scenarios
Reuse the same GPX and generate different activity scenarios without importing again.

### Device Profiles
Generate FIT output using configurable recording/device profiles.

# CYCLING SIMULATION

Cycling uses **speed** as the primary UI metric.

The engine is terrain-first.

Behavior:

- uphill → speed generally decreases
- flat → speed relatively stable
- downhill → speed naturally increases
- accelerating → gradual
- braking/decelerating → gradual

Avoid abrupt jumps.

Good:

`27 → 29 → 32 → 35 → 38 → 41 → 44 → 42 → 39`

Bad:

`27 → 27 → 44 → 29`

Do NOT generate constant speed.

Do NOT randomly generate point-by-point speed.

Do NOT globally multiply all speeds by one factor.

---

# TARGET AVERAGE SPEED

Target average speed is a **final aggregate target**, not a point-by-point speed target.

Example:

Target Average:

`28.0 km/h`

The engine must:

1. Generate terrain-driven baseline speed.
2. Calculate moving time.
3. Calculate resulting average speed.
4. Compare against target.
5. Adjust strategically.
6. Preserve terrain relationships.
7. Recalculate.
8. Stop when the target is achieved within configured tolerance or determined infeasible.

Do not destroy the terrain profile simply to hit the target.

If the target is physically infeasible for the route/profile, report the best achievable value instead of fabricating impossible performance.

---

# MAXIMUM SPEED

If the user requests:

`Max Speed = 50 km/h`

Do not simply insert `50` somewhere.

Analyze actual downhill candidates based on:

- gradient
- downhill length
- preceding speed
- following terrain
- acceleration potential
- braking/deceleration opportunity

Rank candidates.

Select a plausible downhill.

Generate natural acceleration toward the maximum.

Decelerate naturally afterward.

If 50 km/h cannot reasonably be achieved on the route, report the naturally achievable maximum instead.

---

# RUNNING

Running uses pace in the user interface.

Example:

`5:30 min/km`

Terrain behavior:

- uphill → slower pace
- flat → stable pace
- downhill → faster pace

Internally speed can be used:

`speed = 60 / pace`

But the user should primarily see pace.

# MOVING TIME VS TOTAL TIME

Keep these values separate.

### Moving Time
Time actually spent moving.

### Total Time
Elapsed time from activity start to activity end, including pauses/stops.

Moving average speed/pace must use moving time.

Total time must include pauses.

If the source GPX contains timestamp gaps, preserve and interpret those gaps when valid.

If timestamps are absent, generate chronological timestamps from simulated movement.

Never produce timestamp inconsistencies.
